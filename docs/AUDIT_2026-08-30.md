# End-to-End Product, Security, Deployment, and UX Audit

Date: 2026-08-30
Scope: draft PR #26, GitHub Actions, Railway API/web services, application architecture,
security controls, core workflows, operations, documentation, and responsive UI/UX.

## Executive assessment

PR #26 was not safe to deploy as originally submitted. Its web application could
replace real API behavior with a permissive mock login, fabricated records, and
successful-looking writes. It also weakened production startup guarantees and did
not exercise built containers at runtime in CI. Those paths have been removed and
regression-tested.

The codebase now has a coherent production boundary: the browser talks to a
same-origin Next.js API rewrite, the web service reaches the API over Railway's
private network, production configuration fails closed, migrations run in Railway's
pre-deploy phase, and health checks gate promotion. The system still requires the
Railway variables and external policy decisions listed below before production
approval.

## System and trust boundaries

1. Browser traffic terminates at the Next.js web service.
2. `/api/v1/*` is rewritten server-side to the NestJS API through `API_INTERNAL_URL`.
3. NestJS owns authentication, authorization, CSRF enforcement, validation, audit
   events, workflow transitions, and signed attendance tokens.
4. PostgreSQL stores transactional and identity data. S3-compatible object storage
   stores evidence and absence documents; production startup rejects incomplete
   storage configuration.
5. Railway pre-deploy executes schema deployment and idempotent reference-data seed
   before the API revision is promoted.

## Findings and dispositions

| Severity | Finding | Disposition |
|---|---|---|
| Critical | A catch-all web route accepted demo credentials without server authentication and issued an unsigned JavaScript-readable session cookie. | Fixed: route and demo credentials removed; authentication only uses NestJS. |
| Critical | API client failures could return fabricated operational data and report successful mutations that never persisted. | Fixed: all fallbacks removed; failed reads and writes surface as errors; regression tests added. |
| High | The PR removed the production environment marker and made database migration conditional, allowing an incorrectly configured revision to start. | Fixed: `APP_ENV=production` restored and deployment fails fast. |
| High | QR links defaulted to localhost when the public origin was omitted. | Fixed: production requires an HTTPS `PUBLIC_BASE_URL` pointing to the public web origin. |
| High | Database migration/seed ran in the long-lived API container command rather than a Railway release phase. | Fixed: Railway pre-deploy now performs migration and seed; runtime starts only the API. |
| High | Railway reported repeated API deployment failure, but the authenticated build/runtime logs were unavailable from this environment. | External verification required: authenticate Railway, inspect the failed deployment, set the required variables below, and redeploy. |
| Medium | CI built Docker images without proving the API image could start or answer a health request. | Fixed: CI now boots PostgreSQL and the built API image and probes `/health/live`. |
| Medium | Public access-request errors revealed whether an email belonged to an existing account or pending request. | Fixed: both cases use the same generic response; integration coverage added. |
| Medium | The browser could use credentialed backend traffic without an explicit application CSP/connect policy. | Fixed: restrictive CSP, framing, MIME, referrer, cross-origin opener, and production HSTS headers added. |
| Medium | Absence reminder scheduling swallowed failures, hiding operational incidents. | Fixed: scheduler errors are logged while preserving the next run. |
| Medium | Registration promised an approval email, but account-approval email delivery does not exist. | UI claim fixed; notification/status workflow remains a product gap. |
| Medium | Railway JSON config-as-code is a legacy format scheduled for retirement on 2026-12-01. | Open: migrate both services to Railway Infrastructure as Code before that date. |
| Medium | Public-request throttles and reminder scheduling are process-local. They reset on deploy and do not coordinate multiple replicas. | Accepted only while the API runs one replica; use a shared rate limiter and durable job runner before scaling. |
| Medium | Sixteen business, privacy, retention, SSO/MFA, and field-policy decisions remain unsigned. | Open: resolve `docs/OPEN_QUESTIONS.md` before production operating approval. |
| Low | PR #26 described a complete 17-subcounty/85-ward seed expansion, but the seed file did not change from `main`. | Correct the PR description or implement and verify the claimed dataset separately. |
| Low | Next.js reports missing framework-specific ESLint plugin configuration. | Open engineering-quality improvement; base ESLint and TypeScript checks pass. |

No committed secrets were found in the tracked source. The production dependency
audit reported no known high-severity production vulnerabilities. Evidence uploads
enforce size/type checks and image re-encoding; object writes request server-side
encryption. Authentication is cookie-based with CSRF protection, default-deny guards,
scoped capability checks, password-change enforcement, and audited administrative
actions.

## UX audit and remodel

The interface now uses a unified responsive design system with light/dark themes,
clearer product positioning, denser operational layouts, elevated cards and metrics,
sticky navigation/table headers, explicit empty/loading/error states, mobile navigation,
and reduced-motion support. Keyboard users receive a skip link, visible focus rings,
focusable password visibility controls, and Escape-to-close mobile navigation. Auth
navigation semantics and status announcements were corrected.

Automated checks cover the UI code and API-boundary regressions. Final browser visual
QA remains required because an in-app browser session was unavailable during this
audit. Validate at 320, 768, 1024, and 1440 pixel widths, both themes, keyboard-only
navigation, long tables, empty states, error responses, and the QR check-in flow on a
real phone before release.

## Required Railway configuration

API service:

- `APP_ENV=production`
- `DATABASE_URL` from the PostgreSQL service
- `PUBLIC_BASE_URL=https://${{web.RAILWAY_PUBLIC_DOMAIN}}`
- `SECURE_COOKIES=true`
- a strong `OWNER_SETUP_TOKEN` until bootstrap is completed, then remove/rotate it
- `S3_ENDPOINT`, `S3_REGION`, `S3_BUCKET`, `S3_ACCESS_KEY_ID`, and `S3_SECRET_ACCESS_KEY`
- SMTP variables if reminder email is required

Web service build/runtime:

- `API_INTERNAL_URL=http://${{api.RAILWAY_PRIVATE_DOMAIN}}:4000`
- a generated public domain; the API does not need a public domain for normal browser use

Do not place secrets in `NEXT_PUBLIC_*` variables. Keep API and PostgreSQL on private
networking, and restrict public exposure to the web service unless operational access
to the API is explicitly required.

## Release gate

Before merging or promoting:

1. Review the code changes and correct the PR description's seed-data claim.
2. Authenticate Railway, inspect the prior API failure log, and confirm every required
   variable above is present in the correct service/environment.
3. Redeploy and require green GitHub quality, database, Docker/runtime smoke, web, and
   API Railway deployment checks.
4. Exercise login, forced password change, request approval, roster import, attendance
   QR check-in, absence review, evidence upload, report finalization, and audit review
   against the deployed preview.
5. Complete browser/accessibility QA and obtain policy-owner sign-off on the unresolved
   production rules.
